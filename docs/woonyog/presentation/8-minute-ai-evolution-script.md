# AI로 진화하기 8분 발표 스크립트

이 문서는 6월 18일 과제 발표용 8분 스크립트다.
목표는 RAG, MCP, AI Agent를 단순히 “붙였다”가 아니라, 직접 구현하면서 어떤 판단과 문제를 겪었고 최종적으로 RepoLM 구조로 어떻게 정리했는지 선형적으로 설명하는 것이다.

## 발표 핵심 메시지

> 처음에는 상용 LLM을 API로 호출하면 AI 기능이 된다고 생각했다.
> 그런데 실제로 구현해 보니 중요한 것은 “어떤 데이터를 믿고, 어떻게 잘라 저장하고, 어떤 근거를 꺼내서, 어떤 도구를 제한적으로 실행하게 할 것인가”였다.
> 이번 프로젝트는 그 질문을 RAG, MCP, Agent, 그리고 웹 서비스 구조 안에서 직접 풀어본 과정이다.

## 실제 발표용 8분 압축 대본

아래 대본은 실제 말하기 기준 7분 40초에서 8분 10초 사이를 목표로 한다.
데모가 길어지면 `창빈2`, `우현` 설명을 한 문장씩 더 줄이고, RAG metadata 필드 나열을 생략한다.

### 0:00-0:40 오프닝

안녕하세요. 저는 이번 “AI로 진화하기” 과제를 하면서 상용 LLM을 그냥 API로 호출하는 수준을 넘어서, RAG, MCP, AI Agent가 실제 서비스 안에서 어떻게 맞물려야 하는지 직접 구현해 보려고 했습니다.

처음에는 솔직히 “게시판에 AI 기능 하나 붙이면 되겠지”라고 생각했습니다. 그런데 만들다 보니 핵심은 LLM 자체가 아니라, 어떤 데이터를 믿고, 어떻게 잘라 저장하고, 어떤 근거를 꺼내고, 어떤 도구를 어디까지 실행하게 할지였습니다.

그래서 오늘은 기능 목록보다 제가 개발하면서 고민했던 흐름을 중심으로 발표하겠습니다.

### 0:40-1:25 5개 브랜치 소개

먼저 다섯 브랜치가 각각 다른 방향으로 AI 게시판을 실험했습니다.

창빈2 브랜치는 TeamLog라는 회의록, 회고 협업툴의 기본 구조를 만들었습니다. FastAPI, SQLAlchemy, PostgreSQL을 사용했고, 페이지와 블록 저장 흐름이 중심입니다.

민정 브랜치는 GitHub 레포를 RAG로 분석하는 구조입니다. 레포 파일을 chunk로 나누고, SQL과 ChromaDB에 저장한 뒤 LangGraph로 근거 기반 답변을 만듭니다.

가인 브랜치는 폰트 추천 서비스입니다. 사용자 글을 LLM이 분석하고, RAG로 폰트 가이드를 찾고, MCP로 실제 폰트 DB를 조회해서 추천합니다.

우현 브랜치는 AI Team Sync Board입니다. 게시글, GitHub, Notion 정보를 모아서 오늘 브리핑이나 팀 요약을 만드는 쪽에 가까웠습니다.

그리고 제 브랜치는 RepoLM입니다. NotebookLM처럼 레포, 문서, 메모, 생성 산출물을 source로 저장하고, 그 자료를 근거로 대화하거나 UML, ERD, 변경 요약을 만드는 서비스입니다.

### 1:25-2:15 데모 1 - 가인 브랜치

첫 번째 데모는 가인 브랜치입니다.

여기서 좋은 점은 RAG, MCP, Agent 흐름이 한 기능 안에서 잘 보인다는 것입니다. 사용자가 글을 입력하면 Agent가 먼저 LLM에게 감정, 스타일, 키워드 같은 구조화 분석을 요청합니다.

그 다음 분석 결과를 query로 바꿔서 ChromaDB에 저장된 폰트 선택 가이드를 검색합니다. 그리고 MCP tool로 실제 DB에 있는 후보 폰트를 가져옵니다.

중요한 건 LLM이 마음대로 폰트를 만들어내지 못한다는 점입니다. 후보는 MCP가 DB에서 가져온 것만 쓰고, LLM은 그 안에서 최종 선택만 합니다. 제가 생각한 좋은 Agent의 기본도 이런 형태였습니다. LLM에게 전부 맡기는 게 아니라, 분석, 검색, 도구 실행을 제한된 순서로 조립하는 것입니다.

### 2:15-3:05 데모 2 - 민정 브랜치

두 번째 데모는 민정 브랜치입니다.

이 브랜치는 GitHub 레포를 가져와서 RAG로 답변하는 기본 골격이 명확했습니다. 사용자가 레포와 브랜치를 선택하면 백엔드가 파일을 가져오고, Python이나 Markdown 파일을 chunk로 나눕니다.

SQL에는 index run, file snapshot, chunk metadata를 저장하고, ChromaDB에는 검색용 vector를 저장합니다. 질문할 때는 repository, branch, commit scope를 먼저 확정합니다.

그리고 LangGraph는 retrieve, generate, no-evidence 흐름을 가집니다. 검색 근거가 있으면 답변을 만들고, 없으면 추측하지 않고 근거가 없다고 답합니다. 이 부분을 보면서 RAG에서 중요한 건 검색을 하는 것보다, 근거가 없을 때 멈출 수 있는 구조라고 느꼈습니다.

### 3:05-4:10 내 프로젝트 - RepoLM 문제 정의

이제 제 프로젝트인 RepoLM입니다.

제가 만들고 싶었던 건 단순 게시판 AI가 아니라, 레포와 문서를 기준으로 대화하고 필요한 경우 산출물까지 만드는 작업 공간이었습니다. 그래서 GitHub 레포, Markdown, PDF, URL, 메모, 생성된 UML이나 ERD까지 source로 다시 넣을 수 있게 잡았습니다.

source가 추가되면 백엔드는 source row를 만들고, indexing progress를 SQL에 저장하고, 파일을 읽어서 chunk로 나눈 뒤 SQL과 pgvector에 저장합니다.

여기서 제일 고민한 건 “LLM이 진짜 사용자가 선택한 자료만 보고 답하게 만들 수 있나”였습니다. 그래서 source 선택, file 선택, chunk metadata, citation, 삭제 상태까지 전부 데이터로 남겼습니다.

### 4:10-5:20 RAG 설계

RAG에서 가장 먼저 부딪힌 문제는 청킹이었습니다.

처음에는 그냥 길이 기준으로 자르면 된다고 생각했는데, Markdown, PDF, 코드가 전부 달랐습니다. Markdown은 heading 계층이 중요하고, PDF는 page 정보가 중요하고, 코드는 클래스나 함수 단위가 중요했습니다.

그래서 chunk에 공통 metadata를 붙였습니다. `source_id`, `path`, `format`, `heading_path`, `page`, `line range`, `content_hash`, `prev/next chunk` 같은 정보입니다.

이렇게 저장하면 검색 결과 하나만 쓰는 게 아니라, 필요하면 앞뒤 chunk나 부모 section까지 같이 가져올 수 있습니다. 또 답변에서 파일과 라인 기반 citation을 만들 수 있습니다.

특히 레포 질문에서는 README나 docs보다 실제 소스코드 신뢰도를 더 높게 두었습니다. 문서는 설명이고, 실제 동작은 코드에 있기 때문입니다.

### 5:20-6:25 Agent 설계

Agent에서는 Planner와 Tool을 나눴습니다.

Planner는 사용자의 질문이 일반 대화인지, 레포 설명인지, 최근 변경 요약인지, RAG 검색이 필요한지, UML이나 ERD 생성인지 판단합니다.

Tool은 제한된 실행 단위입니다. 검색 tool, 파일 읽기 tool, artifact 생성 tool이 있더라도 반드시 `source_ids`, `file_paths`, notebook context를 받아야 합니다. 선택되지 않은 source는 검색에도, 파일 읽기에도 쓰지 않게 막았습니다.

그리고 답변 생성 중에 새 채팅이 들어오면 바로 병렬 실행하지 않고 queue에 담도록 했습니다. 동시에 여러 Agent가 같은 대화 상태를 바꾸면 순서와 근거가 꼬일 수 있기 때문입니다.

결국 제가 만든 Agent는 무엇이든 하는 AI가 아니라, 사용자가 선택한 자료 안에서만 근거를 찾고 제한된 도구를 실행하는 AI에 가깝습니다.

### 6:25-7:20 트러블슈팅

문제도 많았습니다.

첫 번째는 배포였습니다. 프론트는 Vercel이나 Cloudflare로 열 수 있는데, 백엔드가 로컬 Docker에 있으면 외부 API, OAuth callback, CORS, secure cookie가 계속 엮였습니다.

두 번째는 권한 문제였습니다. 다른 계정으로 로그인했는데 같은 노트북이 보이는 버그가 있었고, 이건 바로 owner 기준 조회로 고쳤습니다.

세 번째는 indexing progress였습니다. 레포 분석이 오래 걸리면 실패처럼 보였는데, 실제로는 진행 중인 경우가 있었습니다. 그래서 진행 상태를 메모리에 두지 않고 SQL에 저장하고, UI가 다시 조회해도 복구할 수 있게 했습니다.

마지막으로 UML/ERD도 고민이 많았습니다. LLM이 Mermaid를 만들면 문법 오류나 누락이 자주 생겨서, 가능한 부분은 정적 파싱 기반으로 만들고 Mermaid 형식을 더 엄격하게 제한했습니다.

### 7:20-8:00 회고

이번 과제에서 제일 크게 느낀 건 AI 서비스는 LLM 호출 코드보다 데이터와 흐름 설계가 훨씬 어렵다는 점이었습니다.

RAG는 vector DB에 넣는 것으로 끝나지 않았습니다. 어떤 단위로 자르고, 어떤 metadata를 남기고, 근거가 없거나 충돌할 때 어떻게 답할지까지 설계해야 했습니다.

MCP는 작게 구현했지만, 외부 도구를 열어줄 때 scope와 권한이 핵심이라는 걸 배웠습니다. Agent도 자유도를 많이 주는 것보다 제한된 도구를 명확한 상태 안에서 쓰게 하는 게 더 안정적이었습니다.

아직 RAGAS 같은 정량 평가, 더 많은 언어 파싱, 배포 자동화 같은 개선점은 남아 있습니다. 그래도 이번 프로젝트를 통해 React, FastAPI, Postgres, pgvector, RAG, MCP, Agent를 한 흐름으로 연결해 보면서, 앞으로 나만무 프로젝트에서 AI 기능을 설계할 때 기준이 생겼습니다.

감사합니다.

## 상세 대본

### 1. 오프닝 - 학습 목표와 문제의식

안녕하세요. 저는 이번 “AI로 진화하기” 과제를 하면서, 상용 LLM을 그냥 API로 호출하는 것을 넘어서 RAG, MCP, AI Agent가 실제 웹 서비스 안에서 어떻게 동작해야 하는지 직접 구현해 보려고 했습니다.

처음에는 솔직히 “게시판에 AI 기능 하나 붙이면 되겠지”라고 생각했습니다.
그런데 구현하면서 제일 많이 든 생각은, LLM 자체보다 그 앞뒤의 시스템이 훨씬 중요하다는 거였습니다.

예를 들면, 어떤 데이터를 가져올지, 그 데이터를 어떻게 쪼갤지, 검색 결과를 얼마나 믿을지, 문서와 실제 코드가 다르면 무엇을 기준으로 답해야 할지, 그리고 LLM이 외부 도구를 쓸 때 어디까지 허용해야 하는지 같은 문제들이 계속 나왔습니다.

그래서 오늘 발표는 기능 나열보다, 제가 어떤 고민을 했고 그 고민이 어떻게 RAG, MCP, Agent 구조로 이어졌는지를 중심으로 설명하겠습니다.

### 2. 다섯 브랜치의 실험 방향

이번에 저희는 각자 다른 방향으로 AI 게시판을 구현했습니다.

창빈2 브랜치는 TeamLog라는 캘린더 기반 회의록, 회고 협업툴의 기본 구조를 만들었습니다.
FastAPI, SQLAlchemy, PostgreSQL을 사용했고, 회의록 페이지와 블록을 저장하는 흐름이 중심입니다.
AI 기능은 아직 실제 검색이나 답변보다는 pgvector 연결을 확인하는 단계였습니다.

민정 브랜치는 GitHub 레포를 RAG로 분석하는 쪽에 가까웠습니다.
GitHub OAuth로 로그인하고, 레포 파일을 가져와 chunk로 나누고, SQL과 ChromaDB에 저장한 뒤 LangGraph로 답변 흐름을 만들었습니다.
제가 보기에는 RAG의 기본 골격을 가장 명확하게 보여준 브랜치였습니다.

가인 브랜치는 폰트 추천 서비스입니다.
사용자 글을 LLM이 분석하고, RAG로 폰트 선택 가이드를 찾고, MCP로 실제 폰트 DB를 조회한 뒤, 최종적으로 폰트를 추천합니다.
RAG, MCP, Agent가 기능 안에서 제일 직관적으로 이어지는 사례였습니다.

우현 브랜치는 AI Team Sync Board입니다.
게시글, GitHub issue/PR/commit, Notion 문서를 모아서 오늘 브리핑이나 팀 요약을 만드는 구조입니다.
OpenAI JSON Schema와 pgvector 기반 문서 검색을 사용했습니다.

마지막으로 제 woonyong 브랜치는 이 실험들을 바탕으로 RepoLM을 만들었습니다.
NotebookLM처럼 레포, 문서, 메모, 생성 산출물을 source로 저장하고, SQL과 RAG를 기반으로 질문에 답하거나 UML, ERD, 변경 요약을 만드는 서비스입니다.

### 3. 데모 1 - 가인 브랜치 폰트 추천 Agent

첫 번째로 가인 브랜치를 보면, 흐름이 굉장히 AI Agent스럽습니다.

사용자가 글을 입력하면 Agent가 먼저 LLM에게 글 분석을 요청합니다.
여기서 감정, 시각적 특성, 글쓰기 스타일, 에너지, 키워드 같은 구조화된 결과를 만듭니다.

그 다음 이 분석 결과와 원문을 합쳐서 RAG 검색 query를 만들고, ChromaDB에 저장된 폰트 가이드 중 관련 있는 문서를 찾습니다.
그리고 MCP tool을 통해 실제 DB에 있는 후보 폰트 목록을 가져옵니다.

중요한 점은 LLM이 마음대로 폰트를 지어내지 못하게 했다는 겁니다.
후보 폰트는 MCP가 DB에서 가져온 것만 사용하고, 최종 선택도 그 후보 안의 `font_id`만 고르게 되어 있습니다.

즉, 여기서 Agent는 “LLM에게 전부 맡기는 구조”가 아니라, LLM 분석, RAG 근거, MCP DB 조회를 순서대로 조립하는 역할을 합니다.
이게 제가 생각하는 좋은 Agent의 기본 형태였습니다.

### 4. 데모 2 - 민정 브랜치 GitHub RAG/LangGraph

두 번째는 민정 브랜치입니다.

이 브랜치는 GitHub 레포를 분석해서 RAG로 답변하는 흐름이 있습니다.
사용자가 GitHub로 로그인하고 레포와 브랜치를 선택하면, 백엔드가 GitHub 파일을 가져오고 Python이나 Markdown 파일을 chunk로 나눕니다.

그 다음 SQL에는 index run, file snapshot, chunk metadata를 저장하고, ChromaDB에는 검색용 vector를 저장합니다.
질문할 때는 먼저 어떤 repository, branch, commit 기준으로 답변할지 SQL에서 확정합니다.

그리고 LangGraph는 아주 단순하지만 중요한 흐름을 가집니다.
`retrieve_vector`에서 근거를 검색하고, 근거가 있으면 `generate_answer`로 가고, 없으면 LLM을 호출하지 않고 `no_evidence` 답변을 만듭니다.

이 구조를 보면서 저는 RAG에서 중요한 게 “검색을 했는가”가 아니라, “검색 근거가 없을 때 추측을 막는가”라는 점이라고 느꼈습니다.

### 5. 내 프로젝트 - RepoLM 문제 정의

이제 제 프로젝트인 RepoLM을 설명하겠습니다.

제가 만들고 싶었던 것은 단순 게시판 AI가 아니라, 레포와 문서를 근거로 대화하고, 필요한 경우 UML이나 ERD 같은 산출물까지 만들 수 있는 작업 공간이었습니다.
컨셉은 NotebookLM인데, 대상이 문서만이 아니라 GitHub repo와 소스코드까지 포함되는 RepoLM입니다.

사용자는 노트북을 만들고, GitHub 레포, Markdown, PDF, URL, 메모, 또는 생성된 산출물을 source로 추가할 수 있습니다.
그러면 백엔드는 source row를 만들고, indexing progress를 저장하고, 파일을 읽어서 chunk로 나누고, SQL과 pgvector에 저장합니다.

여기서 제가 계속 고민한 부분은 “어떻게 해야 LLM이 진짜 내가 넣은 자료를 기준으로 답하게 할 수 있을까”였습니다.
그래서 source 선택, file 선택, chunk metadata, citation, 진행률, 삭제 상태까지 전부 SQL에 남기는 방향으로 설계했습니다.

### 6. RAG 설계 - 청킹, 저장, 검색

RAG에서 가장 먼저 부딪힌 문제는 청킹이었습니다.

처음에는 그냥 일정 길이로 자르면 된다고 생각했는데, Markdown, PDF, 코드, plain text는 읽는 방식이 전부 달랐습니다.
Markdown은 heading 계층이 중요하고, PDF는 page 정보가 중요하고, 코드는 함수나 클래스 단위가 중요합니다.

그래서 공통 chunk metadata를 만들었습니다.
`source_id`, `path`, `format`, `heading_path`, `page`, `start_line`, `end_line`, `content_hash`, `parent_chunk_id`, `prev_chunk_id`, `next_chunk_id` 같은 값입니다.

이렇게 저장해 두면 검색 결과 하나만 가져오는 게 아니라, 필요하면 부모 section이나 앞뒤 chunk까지 같이 확장할 수 있습니다.
또 답변에서 “이 내용은 어떤 파일 몇 번째 줄 근거다”라고 citation을 만들 수 있습니다.

검색은 vector search만 믿지 않고 keyword search와 합치려고 했습니다.
질문을 여러 query로 나누고, 검색 결과를 RRF 방식으로 병합한 다음, source scope와 file scope를 다시 필터링합니다.

특히 레포에 대해 질문할 때는 README나 docs보다 실제 소스코드의 신뢰도를 더 높게 두었습니다.
문서는 설명이고, 실제 동작은 코드에 있기 때문에, 코드 질문이라면 `.py`, `.ts`, `.tsx`, `.sql` 근거를 우선하도록 했습니다.

### 7. AI Agent 설계 - Planner와 Tool

Agent 쪽에서 제가 가장 조심한 부분은 LLM이 너무 자유롭게 행동하지 않게 하는 것이었습니다.

그래서 Planner와 Tool을 분리했습니다.
Planner는 사용자의 질문이 일반 대화인지, 레포 설명인지, 최근 변경 요약인지, RAG 검색이 필요한지, UML/ERD 산출물이 필요한지 판단합니다.

Tool은 실행 단위입니다.
예를 들어 검색 tool, 파일 읽기 tool, artifact 생성 tool이 있더라도 반드시 `source_ids`, `file_paths`, notebook context를 받아야 합니다.
선택되지 않은 source나 file은 검색에도, tool read에도 쓰지 않게 막았습니다.

즉, Agent는 “무엇이든 할 수 있는 AI”가 아니라 “사용자가 선택한 자료 안에서만 근거를 찾아 실행하는 AI”가 되도록 했습니다.

또 채팅에서는 한 번 답변이 생성 중일 때 새 질문이 들어오면 바로 병렬 실행하지 않고 queue에 담도록 했습니다.
이것도 실제 서비스에서는 중요했습니다.
동시에 여러 agent가 같은 대화 상태를 바꾸면 답변 순서와 근거가 꼬일 수 있기 때문입니다.

### 8. 트러블슈팅과 구현 문제

개발하면서 문제도 많았습니다.

첫 번째는 배포였습니다.
프론트는 Vercel이나 Cloudflare로 열 수 있는데, 백엔드가 로컬 Docker에 있으면 외부에서 API가 안 붙는 문제가 생겼습니다.
그래서 Cloudflare tunnel, CORS, GitHub OAuth callback URL, cookie secure 옵션을 계속 맞춰야 했습니다.

두 번째는 로그인과 권한 문제였습니다.
다른 계정으로 로그인해도 같은 노트북이 보이는 버그가 있었고, 이건 심각한 문제였습니다.
노트북과 source를 반드시 owner 기준으로 조회하도록 바꾸면서 권한 분리를 다시 확인했습니다.

세 번째는 indexing progress였습니다.
레포 분석이 오래 걸리면 실패처럼 보이는 문제가 있었습니다.
실제로는 진행 중인데 SSE나 polling이 끊기면 UI가 멈춘 것처럼 보였기 때문에, SQL에 progress를 저장하고 상태를 계속 복구할 수 있게 했습니다.

네 번째는 UML/ERD였습니다.
LLM이 Mermaid를 만들면 문법 오류가 나거나, 너무 일부만 그리거나, 관계가 빠지는 문제가 있었습니다.
그래서 가능한 부분은 LLM이 아니라 정적 파싱 기반으로 만들고, UML은 classDiagram, ERD는 erDiagram으로 통일했습니다.

### 9. 회고와 다음 개선

이번 과제를 하면서 제일 크게 느낀 건, AI 서비스는 “LLM 호출 코드”보다 “데이터와 흐름 설계”가 훨씬 어렵다는 점이었습니다.

RAG는 단순히 vector DB에 넣는 게 아니라, 어떤 단위로 자르고, 어떤 메타데이터를 남기고, 검색 결과가 부족할 때 어떻게 처리하고, 충돌할 때 무엇을 더 믿을지까지 설계해야 했습니다.

MCP는 크게 만들지는 못했지만, 외부 도구를 LLM에게 열어줄 때는 권한과 scope가 핵심이라는 걸 배웠습니다.
Agent도 마찬가지로, 자유도를 주는 것보다 제한된 도구를 명확한 상태 안에서 쓰게 하는 게 더 중요했습니다.

아직 개선할 점도 많습니다.
첫째, RAG 품질을 정량 평가하는 RAGAS 같은 평가 루프가 더 필요합니다.
둘째, UML/ERD나 변경요약은 더 많은 언어와 프레임워크를 안정적으로 파싱해야 합니다.
셋째, 배포와 OAuth, worker 상태 같은 운영 요소를 처음부터 자동화해야 합니다.

그래도 이번 프로젝트를 통해 React, FastAPI, Postgres, pgvector, RAG, MCP, Agent를 한 번에 연결해 보면서, 앞으로 나만무 프로젝트에서 AI 기능을 붙일 때 어떤 구조로 접근해야 하는지 기준이 생겼습니다.

감사합니다.
