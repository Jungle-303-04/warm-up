## 현재 작업 형식

찬빈은 기능을 계층별로 완벽히 닫기보다, 사용자가 한 번에 흐름을 타볼 수 있도록 세로로 먼저 구현하고 있다.

현재 흐름은 다음과 같다.

1. 백엔드 모델과 API 기반 구축
2. 캘린더 월별 조회 API 추가
3. 프론트 캘린더 화면 구현
4. 로그인/회원가입과 JWT 인증 연결
5. 회의/회고 작성 모달과 저장 후 재조회 연결
6. 로컬 실행 중 생긴 Vite 캐시 ignore 정리

## 구현한 것

백엔드는 FastAPI, SQLAlchemy, Alembic 기반으로 구성했다. 사용자, 페이지, 페이지 블록, 태그, 댓글 모델을 만들었고, 회의와 회고는 별도 테이블이 아니라 `Page` 모델의 `type`으로 구분한다.

인증은 회원가입, 로그인, `/auth/me`, JWT 발급, 현재 사용자 조회까지 만들었다. 프론트에서는 `localStorage`에 토큰을 저장하고, axios 요청 인터셉터에서 `Authorization` 헤더를 붙인다. 401 응답이 오면 토큰을 지우고 전역 로그아웃 이벤트를 발생시킨다.

캘린더는 `FullCalendar`를 사용한다. 현재 보고 있는 년/월을 기준으로 `/pages/calendar`를 호출하고, 받은 회의/회고를 이벤트로 변환해 표시한다. 선택한 날짜의 항목은 오른쪽 패널에 회의록과 회고록으로 나누어 보여준다.

작성 모달은 회의/회고 공통 모달로 만들었다. 제목, 날짜, 시간, 참여자, 태그, 본문 블록을 입력하고 `POST /pages`로 저장한다. 저장 후에는 모달을 닫고 캘린더 목록을 다시 조회한다.

## 고려한 것으로 보이는 것

- 회의와 회고를 하나의 `Page` 구조로 통합해 확장성을 확보하려 했다.
- 본문을 `PageBlock`으로 분리해 문단, 제목, 불릿, 체크리스트, 코드 블록을 지원하려 했다.
- 캘린더는 전체 데이터를 가져오지 않고 현재 월 범위만 조회하도록 했다.
- 토큰 존재 여부만 믿지 않고 `/auth/me`로 유효성을 확인하려 했다.
- 작성 성공 후 UI를 수동으로 조작하지 않고 서버 데이터를 다시 조회하려 했다.
- 학습 내용을 `study/app-auth-flow.md`, `study/jwt-token-flow.md`에 따로 정리해 흐름을 자기 언어로 이해하려 했다.

## 잘한 점

- 로그인부터 작성 후 캘린더 반영까지 핵심 사용자 흐름을 연결했다.
- 캘린더를 직접 구현하지 않고 `FullCalendar`를 사용해 구현 리스크를 줄였다.
- 백엔드 응답 스키마와 프론트 타입을 맞추려는 의식이 있다.
- 참여자/태그 문자열을 배열로 정리하고, 빈 본문 블록을 저장하지 않는 등 입력 정제를 고려했다.
- 로컬 실행 중 생긴 `frontend/.vite/` 캐시를 `.gitignore`에 추가해 개발환경 노이즈를 줄였다.

## 못했거나 위험한 점

- 권한 필터가 일관되지 않다. `/pages/calendar`는 현재 사용자 기준으로 필터링하지만, 목록 조회와 검색은 현재 사용자 필터가 빠져 있다.
- 상세 조회 `GET /pages/{page_id}`에서도 소유자 검사가 보이지 않는다. 페이지 ID를 알면 다른 사용자의 상세를 볼 수 있는 위험이 있다.
- 상세 보기, 회의 상세, 회고 상세 흐름이 아직 `alert` placeholder로 남아 있다.
- 프론트 변경량이 큰데 빌드, 테스트, API 검증 결과가 커밋에서 확인되지 않는다.
- 주석이 학습 메모 역할까지 겸하고 있어 코드가 다소 장황하다. 팀 코드로 정리할 때는 일부 설명을 문서로 빼는 편이 좋다.

## 개선 우선순위

1. 권한 정책을 먼저 통일한다.
   - `get_pages`, `search_pages`, `get_page`에 현재 사용자 필터 또는 명확한 팀 공유 정책을 적용한다.

2. 상세 모달을 만든다.
   - 캘린더 이벤트나 오른쪽 패널 항목 클릭 시 `GET /pages/{id}`로 상세를 불러온다.
   - 처음에는 읽기 전용 상세 모달만 완성한다.

3. 수정/삭제를 연결한다.
   - 이미 백엔드에 `PATCH /pages/{id}`, `DELETE /pages/{id}`가 있으므로 상세 모달 다음 단계로 붙인다.

4. 최소 검증을 추가한다.
   - 프론트 `npm run build`
   - 백엔드 회원가입, 로그인, 페이지 생성, 캘린더 조회, 상세 조회 API 흐름

5. 코드 정리를 한다.
   - 학습 설명 주석은 문서로 옮기고, 코드에는 의도를 설명하는 짧은 주석만 남긴다.

## 사용자가 도울 수 있는 행동

찬빈에게 다음처럼 짧게 방향을 주면 좋다.

```text
지금 방향 좋다. 로그인부터 작성 후 캘린더 반영까지 세로 흐름을 뚫은 건 잘했다.
다음은 기능을 더 늘리기보다 권한 필터를 먼저 통일하고,
캘린더 항목 클릭 시 상세 모달을 띄워라.
그 다음 수정/삭제를 붙이고, 마지막에 빌드와 API 테스트로 한 번 잠그자.
```

확정해주면 좋은 제품 결정은 두 가지다.

- 캘린더는 내 데이터만 볼지, 팀 전체 데이터를 볼지
- 상세 모달은 읽기 전용부터 갈지, 수정까지 한 번에 넣을지
