# RepoPilot 제품 설계 스펙

> 데모가 아니라 **실서비스**. 팀 단위 워크스페이스에서 레포·문서를 항상 인덱싱하고,
> 근거(citation)와 승인(HITL)이 있는 AI 제안으로 계획·일정·산출물을 만든다.

## 1. 절대 원칙 (불변식)

이 원칙은 모든 화면·API가 반드시 지킨다.

1. **데이터 손실 0.** UI에서 hard delete 없음. 모든 삭제는 **soft delete**(휴지통) + **즉시 Undo 토스트**.
   휴지통에서 복구 가능, 영구삭제는 별도 의도적 행위(보존기간 후 또는 명시적 비우기).
2. **항상 되돌릴 수 있다.** 파괴적 행위(삭제·일괄변경·상태전이)는 Undo 또는 이력에서 복원 가능.
   "생성했는데 안 보임 / 지웠는데 안 지워짐" 같은 상태 불일치는 허용 안 함 → 낙관적 UI + 실패 시 자동 롤백 + 명확한 에러 토스트.
3. **모든 변경은 추적된다.** 누가·언제·무엇을(activity log). 제안/결정/일정변경은 이력 보존.
4. **최소 UI, 완전한 행위.** 화면 요소는 최대한 줄이되 필요한 모든 동작은 가능. 키보드 우선
   (커맨드 팔레트 `⌘K`)로 버튼 수를 줄인다.

## 2. 권한 모델 (Notion식, 단순)

- 워크스페이스 **생성자 = Host(첫 Owner)**.
- Owner는 멤버에게 **역할**을 부여: **Owner / Editor(읽기-쓰기) / Viewer(읽기)**. (기본 3개만)
- 권한은 **워크스페이스 스코프**(자원별 세분화는 후순위). 읽기=조회만, 읽기-쓰기=생성·수정·삭제(soft).
- Owner만: 멤버 초대/역할변경/워크스페이스 삭제/키 관리.
- 모든 쓰기 API는 역할을 서버에서 검증(프론트 숨김은 보조).

## 3. 엔티티 모델

```
Workspace (팀, 최상위)
 ├─ Membership (User × Role)               # Owner/Editor/Viewer
 ├─ ApiCredential (암호화)                  # LLM+임베딩 통합 키, 워크스페이스 기본 + 개인 override
 ├─ Source                                  # 지식 소스 (RAG 코퍼스, 워크스페이스 공유)
 │   ├─ type=github_repo (repo·branch)
 │   └─ type=doc/link (기술문서·URL 업로드)
 ├─ IndexJob (Source별 임베딩/동기화 작업)   # 진행률 %, 상태, 이벤트, 스케줄(cron)
 ├─ Thread (채팅 세션)                       # 자체 메모리·맥락, DB 영속·재로딩
 │   └─ Message (user/assistant, citations[])
 ├─ Proposal (에이전트 제안)                 # PENDING→APPROVED/REJECTED, 근거 citation, confidence
 ├─ ScheduleItem (일정/작업)                 # 칸반·캘린더·주간 뷰 공유 객체, status·시간·본문
 ├─ Artifact (산출물)                        # UML/ERD/계획 — Mermaid 등, 버전, 출처 링크
 └─ Notification (인박스)                    # 드리프트·제안·완료 이벤트 (read/dismiss)

공통: 모든 엔티티에 created/updated/deleted_at(soft), created_by. 변경은 ActivityLog.
참조 관계: Message·Proposal·ScheduleItem·Artifact는 Source/파일/커밋을 citation으로 링크.
```

핵심: **레포는 Workspace의 Source로 1회 등록(공유)**, "새 작업"은 새 **Thread**. Thread는
필요 시 일부 Source만 스코프로 좁힌다. (세션마다 재등록·중복임베딩 안 함)

## 4. 화면 구성 — NotebookLM 클론 (Sources / Chat / Studio 3-Pane)

UI/UX는 **NotebookLM을 그대로 차용**한다(혼선 방지 + 깔끔함 유지). 패널 명칭·구성·인터랙션을 동일하게.

```
┌───────────────────────────────────────────────────────────────┐
│ 상단: ◀ 워크스페이스(=노트북) 제목 · ⌘K · 알림 · 계정          │
├──────────────┬──────────────────────────┬─────────────────────┤
│  Sources     │         Chat             │      Studio         │
│ (NotebookLM  │  (근거 기반 대화)         │  (생성 산출물)       │
│  좌측 그대로) │                          │                     │
│ [+ 추가]     │  · 인용칩(▸근거)          │ · UML 다이어그램     │
│ ☑ repo A 92% │  · 추천 질문 chips        │ · ERD               │
│ ☑ repo B ⏳  │  · 제안 카드(승인/반려)   │ · 계획/요약          │
│ ☑ docs.md    │  · 스트리밍 답변          │ · 일정 보드 열기      │
│ ☐ link…      │  하단: 질문 입력창        │ · 저장된 노트        │
│ ───          │  상단 탭: Chat|Board|뷰어 │ (+ 생성 버튼들)      │
│ Threads(대화)│                          │                     │
└──────────────┴──────────────────────────┴─────────────────────┘
```

NotebookLM 매핑:
- **Workspace ≈ Notebook**: Sources·Studio를 공유. 좌상단에서 노트북(워크스페이스) 전환.
- **Sources 패널(좌, NotebookLM 동일)**: "+ 추가"로 레포/문서/링크 연결. 각 소스에 **체크박스**로
  대화 컨텍스트 포함/제외(=NotebookLM 소스 선택), 레포는 **임베딩 진행률 %** 표시. 아래 Threads(대화 이력).
- **Chat 패널(중앙, NotebookLM 동일)**: 근거 인용칩, **추천 질문 chips**, 스트리밍, + 우리 고유의
  **제안 카드(승인/반려)**. 보드/뷰어는 중앙 상단 탭으로만 추가(NotebookLM 깔끔함 유지).
- **Studio 패널(우, NotebookLM 동일)**: NotebookLM의 "오디오 개요/스터디 가이드" 자리에 **우리 산출물**
  (UML·ERD·계획·일정요약 생성 버튼) + 저장된 노트/Artifact 목록. "일정 보드 열기"는 중앙 Board 탭으로.
- **로그인**: GitHub OAuth 버튼 1개.
- **휴지통/활동로그/설정**(멤버·역할·통합 키·동기화 주기·보존정책)은 상단 메뉴.

> 즉 NotebookLM의 3분할(소스/채팅/스튜디오)을 골격으로 두고, 코드 도메인 특화(인덱싱 %, 제안 승인,
> 일정 보드)만 그 안에 얹는다. 새 UI 패러다임을 만들지 않는다.

## 5. 실시간 동기화

- **단방향 푸시(SSE)**: 임베딩 진행률 %, 채팅 스트리밍, 새 알림/제안.
- **협업 편집(WebSocket 브로드캐스트)**: 보드/일정 동시 보기 + presence + 낙관적 적용,
  1단계는 last-write-wins(+충돌 표시), 동시편집 수요 커지면 CRDT 검토.

## 6. LLM·임베딩 키 (통합)

- **채팅 LLM + 임베딩을 하나의 자격증명(같은 제공자)으로 통합** 입력(사용자 결정). UX 단순.
- 저장: **워크스페이스 기본 키 + 개인 override**, **암호화 at-rest**, 클라이언트 노출·로그 금지.
- 우리 백엔드는 이미 LLM/임베딩이 **포트로 제공자 비종속** → "워크스페이스 키 리졸버"만 추가.

## 7. 외부 연동 · 링크 라우팅

- GitHub App: webhook(서명검증) push → 자동 sync(이미 구현). 비공개 레포는 설치 토큰.
- 링크 클릭: **기본 GitHub permalink**(`path:lines@commit`) → 옵션 `vscode.dev` → 설정 시 `vscode://`.

## 8. 페이즈

- **MVP(실사용 최소)**: 로그인 → 워크스페이스 → 레포 연결(진행률) → 근거 채팅 1탭 → 제안 인박스
  → soft delete+undo+권한. (백엔드 대부분 존재)
- **P2**: 일정 보드(칸반/캘린더/주간) + 실시간.
- **P3**: 우 사이드바 산출물(UML/ERD/계획) 생성.
- **P4**: 스케줄 자동 폴링·드리프트 알림 고도화, 문서/링크 소스 업로드.

**백엔드 갭**: 신규 = Workspace/Membership·권한, OAuth+세션, Thread/Message 영속, ScheduleItem·Artifact·
Notification 도메인, 키 볼트(암호화), SSE/WS, soft-delete+휴지통 공통화, 스케줄러.
기존 재사용 = sync·인덱싱·하이브리드 검색·제안/승인·폴링 워커·GitHub 웹훅.

## 9. 디자인 시스템 (React + Tailwind only)

UI 라이브러리 없이 Tailwind 유틸만으로 통일감.
- **토큰**: accent 1색(예: indigo-600) + neutral gray scale, 폰트 1종(Inter/Pretendard),
  radius `rounded-xl`, 그림자 최소, 간격 4/8 배수.
- **공통 컴포넌트**(직접 구현): Button(3종), Card, Chip(Citation/Status), Tab, Toast(Undo 포함),
  Modal, Sidebar, EmptyState, Spinner/ProgressBar.
- **원칙**: 여백 충분, 테두리·구분선 최소, 상태색은 의미별 4색(성공/경고/위험/정보)만.
- 접근성: 키보드 내비, 포커스 링, 명도 대비.

## 10. 당신이 더 결정해야 할 사항

1. **일정(Board)과 GitHub Issues/Projects 관계** — 독립 보드 vs 양방향 동기화? (범위 큼)
2. **소스 연결 해제 시 임베딩 데이터 처리** — 즉시 soft delete + N일 후 영구삭제 기준?
3. **비공개 레포 접근 범위** — 워크스페이스가 어떤 레포까지(설치 단위/선택 단위)?
4. **멤버 초대 방식** — 이메일 링크 vs GitHub 핸들, 워크스페이스당 인원 한도?
5. **모델 선택 노출** — 고정 모델 vs 사용자가 모델 선택?
6. **알림 채널** — 인앱만 vs Slack/이메일까지?
7. **셀프호스트/온프레미스** 지원 여부(보안 민감 팀 대상이면 큼).
8. **산출물 책임** — UML/ERD는 편집 가능 초안인가, 자동 갱신인가?

## 11. 확정된 결정 (2026-06-15)

### 11.1 GitHub 접근 — 신원 vs 데이터 분리

- **로그인/신원 = 멤버 GitHub OAuth**(핸들 식별만). 인원 제한 없음.
- **레포 콘텐츠 접근 = GitHub App 설치 토큰**(개인 토큰 아님). 호스트가 App을 설치하며 워크스페이스에
  레포를 부여 → "호스트 설치가 닿는 레포"가 곧 접근 범위. **"누구 토큰으로 탐색?" 문제 소멸**:
  워커는 사용자 토큰이 아니라 **설치 토큰**으로 인덱싱한다.
- **워커는 공유 세션(워크스페이스×레포×브랜치) 기준 1개**. 사용자 수와 무관.
- **모든 브랜치 인덱싱**(main 한정 아님) — **확정**. 브랜치별 차이를 인식하는 게 목표.
  스냅샷·active-row를 (repo, branch) 단위로 가짐. (비용↑는 감수, 운영 시 제한 옵션은 후순위)

### 11.2 페이지 가시성 — 레포 접근 못 하는 멤버 차단

- 멤버별 **접근 가능 레포 집합**을 OAuth 토큰으로 조회·캐시(`member.accessible_repos`).
- Thread/Source/Artifact는 **의존하는 레포 집합(required_repos)** 을 가진다.
- **가시성 규칙: `required_repos ⊆ member.accessible_repos` 일 때만 노출.** 아니면 목록·인용·스니펫까지
  숨김(부분 redaction). → 레포 권한 없는 멤버에겐 그 페이지가 **공유되지 않는다.**
- 이는 계획 문서의 "retrieval 전 permission filter"와 동일 원칙. Owner/Editor/Viewer(앱 역할)는
  *행위 권한*, 레포 접근은 *데이터 가시성* — 두 층을 AND로 적용.

### 11.3 일정 보드 → GitHub 단방향

- **단방향 Board → GitHub**(보드가 source of truth). 양방향 안 함(단방향이 더 쉽고 안전).
- 임베딩 시 **전용 GitHub Project를 생성**하고 보드 기준으로 덮어 기록.
- ⚠️ **안전장치**: RepoPilot이 만든 이슈(전용 라벨/네임스페이스)만 건드린다. 보드에서 사라진 항목은
  **close**(완전 삭제 아님 — GitHub 이슈는 사실상 삭제 불가/위험). 사람이 만든 기존 이슈는 보존.
  ("보드에 없으면 무조건 삭제"를 글자 그대로 하면 팀의 실제 이슈가 날아가므로 범위를 우리 것으로 한정.)

### 11.4 소스 연결 해제 / 멤버 / 모델 / 알림

- 소스 해제: soft delete 후 **1시간 뒤 영구삭제**(데모). cleanup 스케줄러 cutoff=1h.
- 멤버: GitHub 핸들(OAuth), 인원 한도 없음.
- 모델: **사용자 선택 UI는 두되 OpenAI만 구현**, 나머지 provider는 미구현 표시.
- 알림: 가능하면 메일, 어려우면 인앱만. 확장은 후순위.

### 11.5 키 — 플랫폼 관리형 키 + 구독 (확정)

- **BYO 키 안 함.** 플랫폼이 **자체 OpenAI 키**로 인덱싱·임베딩·에이전트·대화를 전부 수행하고,
  사용량은 **구독료**로 과금. (사용자 키 입력·볼트 UI 불필요 → 가장 단순.)
- 구현: 키는 **서버 환경(시크릿)** 에만 존재, 사용량은 워크스페이스 단위로 미터링(과금 근거).
  멀티 provider는 미구현(OpenAI만), 모델 선택 UI만 노출.

### 11.6 Thread 소스 범위 — "실제 LLM 챗 기준" (확정)

- **각 Thread는 (a) 선택된 소스 부분집합 + (b) 그 Thread의 메시지 이력만**을 컨텍스트로 쓴다.
  Thread 간 맥락은 섞이지 않는다. 기본값=접근 가능한 전체 소스, 사용자가 좁힐 수 있음(NotebookLM 소스 선택).
- 이유(왜 이 기준인가):
  1. **컨텍스트 윈도우 한계** — 모든 소스·전체 이력을 매번 넣을 수 없다. 범위를 정해 RAG로 필요한
     청크만 검색해 넣는 게 유일하게 확장 가능한 방식.
  2. **답변 품질** — 범위가 좁을수록 노이즈가 줄어 정확도↑(ChatGPT/Claude의 대화 독립성과 동일 철학).
  3. **사용자 통제·예측성** — "이 작업에서 AI가 무엇을 아는지"를 사용자가 명시(NotebookLM 체크박스).
  4. **권한** — Thread 범위를 멤버가 접근 가능한 소스로 제한 → 가시성 규칙(11.2)과 자연 결합.
- 즉 **ChatGPT/Claude(대화=독립 메모리) + NotebookLM(소스 선택)** 의 사실상 표준을 그대로 채택.

### 11.7 기타 확정
