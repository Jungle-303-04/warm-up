# Notion Project Ops

## 기준

노션 팀 운영은 `프로젝트`, `회의`, `작업` 세 축으로 본다.

괜히 DB를 더 만들지 않는다.
헷갈리면 일단 `작업`을 본다.
회의는 근거고, 작업은 실행이고, 프로젝트는 큰 단위다.

이 프로젝트의 기본 Notion 팀스페이스는 `4팀`이다.
다른 팀스페이스가 명시되지 않으면 `4팀`을 기준으로 찾는다.

## 먼저 확인할 것

Notion을 수정하기 전에는 현재 DB 스키마를 먼저 확인한다.

- `프로젝트` DB: 큰 목표 단위
- `회의` DB: 논의, 결정, 후속 조치의 출처
- `작업` DB: 담당자가 실제로 실행할 단위

기존 항목이 있으면 새로 만들기보다 업데이트한다.
중복 DB, 중복 보기, 의미 없는 빈 페이지는 만들지 않는다.

## DB 사용 규칙

`프로젝트`는 큰 목표만 담는다.

- 프로젝트 이름, 상태, 기간, 담당자, 참여자를 채운다.
- 관련 회의와 작업을 연결한다.
- 세부 할 일은 프로젝트 본문에 길게 쓰지 말고 `작업`으로 뺀다.
- 구현 프로젝트라면 본문은 파일 목록이 아니라 실제로 동작하게 된 결과, 실행 흐름, 검증 결과, 관련 커밋을 먼저 쓴다.
- 파일 경로는 보조 정보다. 본문 마지막의 `관련 파일`에만 짧게 둔다.

`회의`는 결정의 근거다.

- 회의 날짜를 반드시 넣는다.
- 참석자, 작성자, 참여자를 가능한 만큼 채운다.
- 결정 사항은 짧고 명확하게 쓴다.
- 회의에서 나온 실행 항목은 `작업`으로 만들고 후속 조치에 연결한다.

`작업`은 실행 단위다.

- 작업 이름은 바로 실행 가능한 문장으로 쓴다.
- 담당자, 기간, 상태, 프로젝트를 채운다.
- 회의에서 나온 작업이면 회의도 연결한다.
- 상태는 DB에 있는 기존 옵션만 쓴다. 보통 `시작하지 않음`, `진행 중`, `보류 중`, `완료`를 사용한다.
- 구현 작업의 본문은 `목표`, `실제 구현`, `동작 확인`, `완료 기준` 순서로 짧게 정리한다.
- `관련 파일`만 있는 작업은 만들지 않는다. 파일을 적어야 한다면 구현 설명 뒤에 보조 정보로 둔다.

## 구현 기록 작성

코드 변경을 Notion 프로젝트와 작업으로 정리할 때는 아래 순서로 판단한다.

1. 사용자가 얻은 실행 가능한 결과가 무엇인지 먼저 쓴다.
2. 시스템이 어떤 흐름으로 동작하는지 단계 단위로 쓴다.
3. 실제로 확인한 명령과 응답을 쓴다.
4. 관련 커밋을 남긴다.
5. 관련 파일은 마지막에만 보조로 남긴다.

좋은 구현 프로젝트 본문 구조:

- `목표`: 왜 이 프로젝트를 만들었는지
- `구현된 동작`: 사용자가 실행하거나 확인할 수 있는 결과
- `파이프라인 흐름`: 입력부터 출력까지의 처리 순서
- `검증`: 실행한 명령, 통과한 테스트, 확인한 API 응답
- `관련 커밋`: 추적 가능한 커밋 목록
- `관련 파일`: 필요한 경우에만 최소 경로

좋은 구현 작업 본문 구조:

- `목표`: 이 작업이 맡은 책임
- `실제 구현`: 코드가 어떤 동작을 하게 되었는지
- `동작 확인`: 어떤 방식으로 확인했는지
- `완료 기준`: 완료로 볼 수 있는 조건
- `관련 파일`: 필요한 경우에만 최소 경로

피할 것:

- 변경 파일만 나열하기
- "구성했다", "추가했다"만 쓰고 동작을 설명하지 않기
- 검증 명령이나 API 응답을 생략하기
- 이미 커밋된 구현과 Notion 설명이 어긋나게 두기

## 회의록 처리

사용자가 회의록을 주면 아래 순서로 처리한다.

1. 회의 내용을 `회의` DB에 남긴다.
2. 결정 사항을 짧게 정리한다.
3. 실행할 일은 `작업` DB로 분리한다.
4. 각 작업에 담당자, 기간, 상태, 프로젝트, 회의를 연결한다.
5. 마지막에 만든 항목과 남은 애매한 점만 짧게 보고한다.

담당자나 날짜가 없으면 추측해서 확정하지 않는다.
대신 누락된 항목을 따로 표시하고, 임시 상태는 `시작하지 않음`으로 둔다.

## 일정 처리

일정은 별도 DB부터 찾지 않는다.
작업의 `기간`으로 캘린더와 타임라인을 보게 만든다.

프로젝트 전체 기간이 필요한 경우에만 `프로젝트`의 기간을 갱신한다.
회의 일정은 `회의 날짜`에 넣는다.
상대 날짜는 사용자의 현재 시간대를 기준으로 절대 날짜로 바꿔 기록한다.
예를 들어 2026-06-10에 사용자가 "내일까지"라고 하면 기간은 2026-06-10부터 2026-06-11까지로 둔다.

## 상태 점검

사용자가 "밀린 것", "이번주 할 일", "진행 상황"을 물으면 `작업` 기준으로 본다.

우선순위는 아래 순서다.

1. 기간이 지났는데 완료가 아닌 작업
2. 이번주 기간이 있는 작업
3. 상태가 비어 있는 작업
4. 담당자가 비어 있는 작업
5. 회의 후속 조치인데 작업으로 연결되지 않은 항목

응답은 판단부터 말한다.
설명을 길게 늘리지 않는다.

## 말투

한국어로 답한다.
너무 정제된 문서체보다 사용자가 직접 정리한 것 같은 말투를 쓴다.

좋은 예:

- "이건 회의로 남기고, 실행할 건 작업으로 뺄게."
- "프로젝트에 길게 쓰기보다 작업으로 분리하는 게 맞아."
- "상태랑 기간이 없어서 캘린더에서 안 보일 수 있어. 이 부분부터 채울게."

피할 것:

- 템플릿 설명을 길게 늘어놓기
- 새 DB를 쉽게 추가하기
- 이미 있는 작업을 또 만들기
- 담당자나 날짜를 근거 없이 확정하기
