# Notion Personal Plan Sync

## 기준

이 스킬은 개인 작업 계획과 실제 레포 상태를 맞출 때 쓴다.
Notion은 계획과 의도의 근거이고, 코드는 구현 사실의 근거다.
둘 중 하나만 보고 확정하지 않는다.

기본 Notion 팀스페이스는 `4팀`이다.
다른 팀스페이스나 DB가 명시되지 않으면 기존 `프로젝트`, `회의`, `작업` DB를 우선한다.
새 DB나 새 속성은 만들지 않는다.

관련 규칙:

- Notion DB 운영은 `docs/skills/notion-project-ops/SKILL.md`를 따른다.
- 코드와 문서 검증은 `docs/skills/repo-context-review/SKILL.md`를 따른다.
- 승인 없이 Notion 페이지, 작업 상태, 소스코드를 수정하지 않는다.

## 사용 시점

사용자가 아래처럼 말하면 이 스킬을 쓴다.

- "내 Notion 계획이랑 코드가 맞는지 봐줘"
- "현재 브랜치 기준으로 내가 해야 할 작업을 알려줘"
- "내 작업노트에서 구현할 항목을 찾아줘"
- "코드와 계획이 다르면 Notion 계획을 어떻게 바꿔야 할지 제안해줘"
- "완료된 코드 기준으로 작업 상태를 바꿔도 되는지 봐줘"

## 1. 본인 식별

먼저 현재 사용자가 누구인지 근거를 모은다.

확인할 것:

1. Notion connector나 세션에서 현재 사용자 정보를 확인한다.
2. Notion 사용자 ID, 이름, 이메일 중 확인 가능한 값을 기록한다.
3. `git branch --show-current`로 현재 브랜치를 확인한다.
4. `git config user.name`, `git config user.email`을 확인한다.
5. 필요하면 현재 브랜치의 최근 커밋 작성자도 확인한다.

식별 근거의 강도:

- 강함: Notion `담당자`, `참여자`, `작성자`가 현재 Notion 사용자와 일치한다.
- 중간: git author 이메일이나 이름이 Notion 사용자와 일치한다.
- 약함: 브랜치명, 프로젝트명, 페이지 제목에 사용자 이름이 포함된다.

강한 근거가 없으면 추측해서 확정하지 않는다.
사용자에게 "Notion에서 본인으로 볼 이름이나 이메일이 무엇인지" 짧게 묻는다.

## 2. 개인 작업 후보 찾기

Notion에서는 기존 DB와 페이지를 먼저 찾는다.

우선순위:

1. `작업` DB에서 현재 사용자가 `담당자` 또는 `참여자`인 항목
2. `작업` DB에서 현재 사용자가 `작성자`인 항목
3. `프로젝트` DB에서 현재 사용자가 `담당자` 또는 `참여자`인 항목의 연결 작업
4. `작업노트`, 개인 계획, 브랜치명, repo 이름과 연결된 페이지
5. 회의 후속 조치 중 현재 사용자가 담당자인 항목

상태 우선순위:

1. `진행 중`
2. 기간이 지났거나 오늘/이번 주에 걸린 `시작하지 않음`
3. 코드 근거가 있는데 아직 `완료`가 아닌 항목
4. 구현이 막힌 `보류 중`
5. `완료`지만 코드 근거가 부족하거나 계획과 다른 항목

같은 의미의 작업이 여러 개면 새로 만들지 말고 중복 후보로 표시한다.

## 3. 코드 상태 확인

현재 브랜치와 실제 구현을 확인한다.

기본 명령:

```bash
git branch --show-current
git status --short
git diff --stat
git log --oneline --decorate -n 20
```

필요하면 기준 브랜치와 비교한다.
기준 브랜치를 모르면 `main`, `master`, 원격 기본 브랜치 순서로 확인한다.

작업 항목에서 뽑을 검색 키워드:

- 기능명, 화면명, API 이름
- 파일 경로, 패키지명, 모듈명
- Notion 작업 제목의 핵심 명사
- 완료 기준에 적힌 명령, endpoint, component, test 이름

검색은 `rg`를 먼저 쓴다.
구현 파일, 설정, 테스트, 문서를 같이 본다.

## 4. 계획과 코드 비교

각 작업을 아래 상태로 판정한다.

- `계획대로 구현됨`: Notion의 목표와 완료 기준이 현재 코드에서 확인된다.
- `코드가 앞서감`: 코드에는 구현이 있는데 Notion 작업, 설명, 상태가 따라오지 못했다.
- `계획이 앞서감`: Notion에는 구현 계획이 있지만 코드 근거가 없다.
- `계획과 코드가 다름`: 둘 다 근거가 있지만 구현 방향이나 범위가 다르다.
- `판단 보류`: 외부 서비스, 숨겨진 브랜치, 불명확한 이름 때문에 확정할 수 없다.

판정에는 반드시 근거를 붙인다.
근거는 Notion 페이지 이름과 레포 파일 경로를 함께 적는다.

## 5. 지금 구현할 항목 설명

사용자에게 먼저 알려줄 것은 "지금 무엇을 구현해야 하는가"다.

응답 순서:

1. 본인 식별 근거
2. 현재 브랜치와 레포 상태
3. 지금 구현해야 하는 작업 1~3개
4. 왜 이 작업이 우선인지
5. 코드와 계획의 차이
6. 제안할 Notion 수정 또는 코드 수정

작업 설명은 실행 가능해야 한다.
"정리 필요" 같은 넓은 표현만 쓰지 않는다.

좋은 형태:

```text
지금은 `작업 A`를 먼저 보는 게 맞아.
Notion 상태는 `진행 중`이고, 현재 브랜치에도 관련 파일 변경이 있어.
다만 완료 기준에 있는 API 테스트 근거가 아직 없어서 `완료`로 바꾸기는 이르다.
제안: 작업 본문에 현재 구현 파일과 남은 검증 명령을 추가하고, 상태는 `진행 중`으로 유지.
```

## 6. 수정 제안과 승인

Notion이나 코드를 바꾸기 전에는 수정안을 먼저 보여준다.

Notion 수정안에는 아래를 포함한다.

- 대상 페이지 또는 작업 이름
- 바꿀 속성: 상태, 기간, 담당자, 프로젝트 연결 등
- 본문에 추가할 내용: 현재 코드 근거, 남은 구현, 검증 명령, 관련 파일
- 바꾸지 않을 항목과 이유

코드 수정안에는 아래를 포함한다.

- 바꿀 파일
- 구현할 동작
- 확인할 명령
- Notion 계획과 연결되는 완료 기준

사용자가 승인하면 그때 수정한다.
승인이 애매하면 "수정까지 진행해도 될까요?"라고 묻고 멈춘다.

## 7. Notion 갱신 규칙

상태는 DB의 기존 옵션만 쓴다.
기본 상태는 `시작하지 않음`, `진행 중`, `보류 중`, `완료`다.

상태 변경 기준:

- `진행 중`: 현재 브랜치나 작업 흔적이 있고 완료 기준은 아직 부족하다.
- `완료`: 완료 기준과 검증 근거가 모두 확인된다.
- `보류 중`: 외부 결정, 권한, 의존 작업 때문에 멈췄다.
- `시작하지 않음`: 관련 코드 변경이나 실행 근거가 없다.

본문에는 파일 목록만 적지 않는다.
아래 순서로 짧게 남긴다.

```text
목표
현재 코드 근거
남은 구현
동작 확인
관련 파일
```

브랜치명은 새 속성이 이미 있을 때만 속성에 넣는다.
없으면 작업 본문에 보조 정보로 남긴다.

## 8. 주의

- 브랜치명만으로 담당자를 확정하지 않는다.
- 작성자만 같다고 현재 담당 작업이라고 단정하지 않는다.
- 코드가 없다고 계획을 삭제하지 않는다. 먼저 `계획이 앞서감`으로 분류한다.
- 코드가 있다고 바로 `완료`로 바꾸지 않는다. 완료 기준과 검증 근거를 본다.
- Notion과 코드가 다르면 어느 쪽이 틀렸다고 단정하지 말고, 선택지를 제안한다.
- 상대 날짜는 사용자의 시간대를 기준으로 절대 날짜로 바꿔 말한다.
