# 운영 컨벤션

이 문서는 이 프로젝트의 운영 규칙을 `docs/config/`에서 관리하기 위한 기준이다.
루트에는 실행에 필요한 코드와 설정만 두고, 문서 성격의 규칙은 이 폴더 아래에 둔다.

## 운영 원칙

- Notion 운영 기준은 `4팀` 팀스페이스의 `팀 협업 허브`다.
- 팀 운영 데이터베이스는 `프로젝트`, `회의`, `작업` 세 가지를 기준으로 한다.
- 팀원은 각자 프로젝트를 만들 수 있다.
- 실행 기준, 로컬 명령, 검증 방법은 각 프로젝트의 본문과 작업에 따로 남긴다.
- 새 DB를 쉽게 만들지 않는다. 먼저 기존 DB의 속성, 보기, 관계로 해결한다.
- 회의는 근거, 작업은 실행, 프로젝트는 큰 단위다.
- 일정은 별도 운영 DB로 늘리지 않고 `프로젝트.기간`, `회의.회의 날짜`, `작업.기간`으로 본다.
- 상태값은 현재 Notion DB의 기존 옵션을 사용한다: `시작하지 않음`, `진행 중`, `보류 중`, `완료`.
- 상세 설명, 근거, GitHub 링크, 결정 내용은 속성으로 늘리지 않고 각 페이지 본문에 작성한다.

## Notion 작성 규칙

- `프로젝트`는 큰 목표 단위로만 만든다.
- 팀원별 프로젝트는 별도 `프로젝트` 항목으로 분리한다.
- 프로젝트에는 `프로젝트 이름`, `상태`, `기간`, `담당자`, `참여자`, 관련 `회의`, 관련 `작업`을 연결한다.
- 세부 할 일은 프로젝트 본문에 길게 쓰지 않고 `작업`으로 분리한다.
- `회의`는 논의와 결정의 출처로 만든다.
- 회의에는 `회의 날짜`, `작성자`, `참석자`, `참여자`, `프로젝트`, `결정 사항`, `후속 조치`를 가능한 만큼 채운다.
- 회의에서 나온 실행 항목은 반드시 `작업`으로 만들고 회의의 `후속 조치`에 연결한다.
- `작업`은 담당자가 바로 실행할 수 있는 단위로 만든다.
- 작업에는 `작업 이름`, `상태`, `기간`, `담당자`, `참여자`, `프로젝트`, 관련 `회의`를 가능한 만큼 채운다.
- 담당자나 기간이 불명확하면 추측해서 확정하지 않고, 본문에 누락 사항을 남긴다.
- 완료된 프로젝트, 회의 후속 작업, 작업은 `완료`로 닫는다.

## Notion 보기 규칙

- `팀 협업 허브`는 팀원이 바로 쓰는 보기만 둔다.
- 기본 보기 흐름은 `프로젝트`, `회의`, `작업`을 빠르게 들어갈 수 있게 유지한다.
- 보드와 캘린더는 `작업` 기준으로 보는 것을 우선한다.
- 회의 목록은 최신 회의와 후속 조치가 바로 보이게 유지한다.
- 데이터베이스 관리용 페이지는 필요하지만, 팀원이 매일 보는 화면에서는 과하게 드러내지 않는다.

## 문서 작성 규칙

- 루트 문서는 길게 늘리지 않는다. 루트에는 프로젝트 목적과 실행 입구만 둔다.
- 학습과 기술 설명은 `docs/woonyong/full-stack-tech-loadmap/` 또는 `docs/woonyong/ai-implementation/`에 둔다.
- RepoLM 제품 기획은 `docs/woonyong/ai-dev-workspace/`에 둔다.
- 스킬 지도는 `docs/skills/README.md`에 둔다.
- 운영/문서/Git 규칙은 `docs/config/`에 둔다.
- 문서는 한국어로 작성하되, 기술명과 API 이름은 공식 영문 표기를 유지한다.
- 새 문서를 추가하면 가장 가까운 `README.md` 인덱스에 링크를 추가한다.
- 문서가 실제 코드나 공식 문서 근거와 어긋날 수 있으면 `검토 필요`로 표시한다.

## Git 규칙

- 기본 전략은 GitHub Flow를 사용한다.
- `main`은 항상 읽을 수 있고 공유 가능한 상태로 유지한다.
- 기능 또는 문서 단위로 짧은 브랜치를 만든다.
- PR은 작게 유지하고, 하나의 PR에 제품 기획과 구현 변경을 과하게 섞지 않는다.
- 이미 공유된 브랜치는 rebase하지 않는다.
- 커밋과 PR 규칙은 `docs/skills/commit-convention/SKILL.md`를 기준으로 한다.

## Commit Convention

커밋 메시지는 아래 형식을 사용한다.

```text
<type>: <한국어 제목>
```

허용 타입:

- `feat`: 사용자 관점의 기능 추가
- `fix`: 버그 수정
- `refactor`: 동작 변화 없는 구조 개선
- `docs`: 문서 변경
- `test`: 테스트 추가 또는 수정
- `chore`: 유지보수
- `style`: 동작에 영향 없는 포맷팅
- `perf`: 성능 개선
- `build`: 빌드 설정 변경
- `ci`: CI 설정 변경
- `revert`: 이전 커밋 되돌리기

제목 규칙:

- 한국어 한 줄로 작성한다.
- 마침표로 끝내지 않는다.
- `수정`, `작업`, `변경`, `업데이트` 같은 넓은 단어만 쓰지 않는다.
- 결과가 드러나게 쓴다.

예시:

```text
docs: 운영 컨벤션과 스킬 인덱스를 추가
docs: AI 구현 로드맵의 RAG 평가 기준을 정리
refactor: 문서 인덱스 구조를 루트 기준으로 단순화
```

## Review Checklist

- 새 문서가 루트 또는 하위 README에서 찾을 수 있는가?
- Notion DB가 `프로젝트`, `회의`, `작업` 기준에서 벗어나지 않았는가?
- 새 DB나 새 속성을 만들기 전에 기존 관계와 보기를 먼저 썼는가?
- 회의에서 나온 실행 항목이 작업으로 분리됐는가?
- 작업에 담당자, 기간, 상태, 프로젝트가 가능한 만큼 채워졌는가?
- 회의에 날짜, 결정 사항, 후속 조치가 연결됐는가?
- 기술 문서가 공식 문서, 레포 파일, 구현 계획 중 하나와 연결되는가?
- 커밋 메시지가 컨벤션을 따른 상태인가?
