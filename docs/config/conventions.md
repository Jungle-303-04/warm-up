# Conventions

이 문서는 이 프로젝트의 운영 규칙을 루트에서 바로 확인하기 위한 기준이다.
세부 문서는 `docs/`에 두고, 팀이 반복해서 지켜야 하는 약속만 여기에 남긴다.

## 운영 원칙

- 모든 실행 항목은 Notion의 `운영 항목` 데이터베이스에서 관리한다.
- 운영 항목의 속성은 단순하게 유지한다: `제목`, `담당자`, `작성자`, `참조자`, `생성 시간`, `시작 시간`, `종료 시간`, `유형`, `상태`.
- `유형`은 `회의`, `일정`, `작업`만 사용한다.
- `상태`는 `대기`, `진행`, `종료`, `보류`만 사용한다.
- 상세 설명, 근거, GitHub 링크, 결정 내용은 속성으로 늘리지 않고 각 페이지 본문에 작성한다.

## Notion 작성 규칙

- 회의는 `유형=회의`로 만들고 참석자와 참조자는 본문 또는 `참조자`에 남긴다.
- 회의에서 나온 실행 항목은 별도 `유형=작업` 항목으로 만든다.
- 일정은 `유형=일정`으로 만들고 `시작 시간`과 `종료 시간`을 반드시 채운다.
- 담당자가 바로 실행할 수 없는 항목은 `대기` 또는 `보류`로 둔다.
- 완료된 회의, 일정, 작업은 `종료`로 닫는다.

## 문서 작성 규칙

- 루트 문서는 길게 늘리지 않는다. 루트에는 목적, 규칙, 인덱스만 둔다.
- 학습과 기술 설명은 `docs/woonyong/full-stack-tech-loadmap/` 또는 `docs/woonyong/ai-implementation/`에 둔다.
- RepoPilot 제품 기획은 `docs/woonyong/ai-dev-workspace/`에 둔다.
- 문서는 한국어로 작성하되, 기술명과 API 이름은 공식 영문 표기를 유지한다.
- 새 문서를 추가하면 가장 가까운 `README.md` 인덱스에 링크를 추가한다.
- 문서가 실제 코드나 공식 문서 근거와 어긋날 수 있으면 `검토 필요`로 표시한다.

## Git 규칙

- 기본 전략은 GitHub Flow를 사용한다.
- `main`은 항상 읽을 수 있고 공유 가능한 상태로 유지한다.
- 기능 또는 문서 단위로 짧은 브랜치를 만든다.
- PR은 작게 유지하고, 하나의 PR에 제품 기획과 구현 변경을 과하게 섞지 않는다.
- 이미 공유된 브랜치는 rebase하지 않는다.

## Commit Convention

커밋 메시지는 아래 형식을 사용한다.

```text
<type>: <한국어 제목>
```

허용 타입:

- `feat`: 사용자 관점의 기능 추가
- `fix`: 버그 수정
- `refactor`: 동작 변화 없는 구조 개선
- `docs`: 문서 변경
- `test`: 테스트 추가 또는 수정
- `chore`: 유지보수
- `style`: 동작에 영향 없는 포맷팅
- `perf`: 성능 개선
- `build`: 빌드 설정 변경
- `ci`: CI 설정 변경
- `revert`: 이전 커밋 되돌리기

제목 규칙:

- 한국어 한 줄로 작성한다.
- 마침표로 끝내지 않는다.
- `수정`, `작업`, `변경`, `업데이트` 같은 넓은 단어만 쓰지 않는다.
- 결과가 드러나게 쓴다.

예시:

```text
docs: 운영 컨벤션과 스킬 인덱스를 추가
docs: AI 구현 로드맵의 RAG 평가 기준을 정리
refactor: 문서 인덱스 구조를 루트 기준으로 단순화
```

## Review Checklist

- 새 문서가 루트 또는 하위 README에서 찾을 수 있는가?
- Notion 운영 항목의 속성이 불필요하게 늘어나지 않았는가?
- 회의에서 나온 실행 항목이 작업으로 분리됐는가?
- 일정에 시작 시간과 종료 시간이 있는가?
- 기술 문서가 공식 문서, 레포 파일, 구현 계획 중 하나와 연결되는가?
- 커밋 메시지가 컨벤션을 따른 상태인가?
