# Komodor 기준 데모 시나리오와 발표 흐름

[[README|README]] / [[projects/README|프로젝트]] / [[projects/final/README|최종 프로젝트]] / [[projects/final/planning/README|기획]] / [[projects/final/planning/komodor-based-demo-scenario|Komodor 기준 데모 시나리오와 발표 흐름]]

## 문서 목적

이 문서는 발표용 데모 UI를 ‹WIKILINK:[https://komodor.com/|Komodor›](https://komodor.com/%7CKomodor%E2%80%BA) 스타일에 맞춰 설계하기 위한 기준 문서다.

목표는 "쿠버네티스를 잘 모르는 사람도 왜 이 서비스가 필요한지 바로 이해하게 만드는 것"이다. 그래서 화면은 복잡한 기술 설명보다 다음 흐름이 먼저 보여야 한다.

1. 서비스가 배포된다.
2. 배포 후 장애가 발생한다.
3. 사용자는 어느 서비스가 문제인지 한눈에 본다.
4. 시스템은 Git 변경, Pod 상태, 로그, 메트릭을 묶어 원인 분석 자료를 만든다.
5. AI는 원인 후보와 수정 방향을 설명한다.
6. 사용자는 검증된 수정 PR을 승인한다.
7. GitOps 방식으로 복구가 기록되고 반영된다.

## 한 문장 정의

우리가 만들려는 서비스는 단순한 Kubernetes 대시보드가 아니라, Git 변경과 운영 상태를 연결해서 장애 원인과 안전한 수정 PR까지 제안하는 AI 기반 GitOps 운영 제어 플랫폼이다.

## Komodor에서 가져올 기준

Komodor는 Kubernetes 운영자가 여러 클러스터, 서비스, 워크로드, 장애, 비용, 자동 복구 정책을 한 화면에서 관리하도록 돕는 상용 서비스다.

우리가 참고할 점은 다음이다.

- 클러스터와 서비스의 건강 상태를 한눈에 보여준다.
- 서비스별로 Healthy, Warning, Unhealthy 같은 상태를 분류한다.
- 이벤트, 로그, Pod 상태, 비용, 리소스 최적화 정보를 한 화면에서 연결한다.
- AI 또는 자동화 기능이 장애 원인과 복구 방향을 제안한다.
- Self-Healing Policy, Audit, 권한, 실행 기록처럼 운영 안전장치를 둔다.

단, 발표에서는 "Komodor를 그대로 만든다"가 아니라 "Komodor처럼 운영 상태를 보기 쉽게 만들고, 우리는 GitOps와 Safe PR 중심으로 확장한다"라고 말해야 한다.

## Komodor와 우리 서비스의 차이

Komodor와 겹치는 부분은 Kubernetes 운영 화면, 서비스 상태, 장애 알림, AI 원인 분석, 복구 제안이다.

우리 서비스의 차별점은 다음 세 가지로 잡는다.

1. Git 변경과 장애를 더 강하게 연결한다.
   - 단순히 현재 Pod가 아픈지 보는 것이 아니라, 어떤 Git 변경이 그 상태를 만들었는지 따라간다.
2. 복구를 클러스터 직접 수정이 아니라 Safe PR로 남긴다.
   - AI가 바로 kubectl 명령을 실행하는 것이 아니라, Git에 남길 수 있는 수정 PR을 만든다.
3. 배포 전 위험 분석과 배포 후 원인 분석을 같은 흐름으로 묶는다.
   - 배포 전에는 "이 변경이 위험한가"를 보고, 배포 후에는 "정말 이 변경 때문에 문제가 생겼는가"를 본다.

## 발표에서 피해야 할 점

발표자는 너무 많은 Kubernetes 용어를 한꺼번에 설명하지 않는다.

다음 단어는 발표 중 쉽게 바꿔 말한다.

| 어려운 표현           | 발표용 표현                     |
| ---------------- | -------------------------- |
| Evidence         | 분석 근거, 분석 자료               |
| RCA              | 원인 분석                      |
| CrashLoopBackOff | 서버가 계속 재시작되는 상태            |
| OOMKilled        | 메모리 부족으로 종료된 상태            |
| Semantic Diff    | 변경 위험 분석                   |
| Scheduling       | Pod를 어느 서버에 둘지 판단하는 과정     |
| Gate             | 배포 전 통과 조건 확인              |
| Safe PR          | 검증된 수정 PR                  |
| Drift            | Git 설정과 실제 클러스터 상태가 달라진 상태 |

## 핵심 페르소나

### 1. 초급 DevOps 담당자

가장 적합한 발표 페르소나다.

이 사용자는 Kubernetes 명령어를 어느 정도 알지만, 장애가 났을 때 Git 변경, Pod 상태, 로그, 메트릭을 빠르게 연결해서 설명하기 어렵다.

발표에서는 이 사람을 기준으로 말한다.

"초급 DevOps 담당자가 결제 서비스 장애를 발견하고, 시스템의 도움을 받아 원인을 이해하고, 수정 PR까지 만드는 흐름"이 가장 이해하기 쉽다.

### 2. 서비스 개발자

개발자는 본인이 만든 변경이 운영 장애로 이어졌는지 알고 싶다.

개발자는 Kubernetes 내부 구조를 깊게 알지 않아도, "내 PR에서 DB 연결 수를 줄인 것이 장애 위험이었구나"를 이해할 수 있어야 한다.

### 3. 운영 리더 또는 리뷰어

운영 리더는 AI가 제안한 조치를 바로 믿기보다, 어떤 근거로 그런 결론을 냈는지 확인하고 승인하고 싶다.

이 사용자에게는 감사 로그, 승인 기록, Safe PR, 배포 결과가 중요하다.

## 추천 데모 시나리오

### 시나리오 제목

새 버전 배포 후 결제 서비스 장애를 AI가 분석하고 Safe PR로 복구한다.

### 시나리오 배경

개발자가 결제 API v2를 배포했다.

변경 내용에는 이미지 버전 변경뿐 아니라 다음 설정 변경이 함께 들어 있었다.

- `DB_POOL_SIZE`: 20에서 5로 감소
- `memory limit`: 512Mi에서 256Mi로 감소
- `replicas`: 3에서 4로 증가

배포 후 결제 서비스에서 문제가 발생한다.

- 일부 Pod가 정상적으로 뜨지 못하고 계속 재시작된다.
- 결제 응답 시간이 180ms에서 2.4초로 증가한다.
- DB timeout 로그가 새로 증가한다.
- 사용 가능한 Pod가 3개 중 1개로 줄어든다.

이때 사용자는 여러 도구를 돌아다니지 않고, 우리 서비스에서 변경, 상태, 로그, 지표, 복구 후보를 한 흐름으로 확인한다.

## 전체 발표 흐름

데모는 다음 7장으로 구성하는 것이 좋다.

1. 메인 Overview: 클러스터와 서비스 상태를 한눈에 보여준다.
2. 장애 서비스 선택: 어떤 서비스가 문제인지 선택한다.
3. 서비스 상세: Pod 상태, 로그, 지표, 최근 변경을 한 화면에 보여준다.
4. 변경 위험 분석: Git 변경이 어떤 운영 위험으로 해석되는지 보여준다.
5. AI 원인 분석 채팅: 사용자가 질문하고 AI가 쉬운 말로 설명한다.
6. Safe PR 제안: AI가 수정 후보를 만들고, 검증과 승인을 기다린다.
7. 복구 결과와 감사 기록: PR 반영 후 상태가 좋아졌고 기록이 남았음을 보여준다.

## 화면 1. 메인 Overview

### 화면 목표

사용자가 처음 들어왔을 때 "지금 어디가 위험한지" 바로 알게 하는 화면이다.

Komodor의 클러스터 목록, 서비스 목록, Health Score 화면을 참고한다.

### 화면 구성

- 왼쪽 사이드바
  - Clusters
  - Overview
  - Health
  - Services
  - Workloads
  - Cost
  - AI Actions
  - Settings
- 상단 요약 카드
  - 전체 클러스터 수
  - 전체 서비스 수
  - 건강한 서비스 수
  - 위험 서비스 수
  - 최근 배포 수
- 중앙 서비스 카드 목록
  - `checkout-api-v2`: Critical
  - `order-api`: Healthy
  - `inventory-api`: Healthy
  - `web-frontend`: Warning
  - `recommend-worker`: Healthy
- 오른쪽 AI 요약 패널
  - "결제 서비스에서 배포 직후 에러율과 응답 시간이 증가했습니다."
  - "최근 Git 변경과 연결된 장애 가능성이 있습니다."
  - "자세히 보기" 버튼

### 이 화면에서 보여줄 기능

- 서비스 상태를 색으로 구분한다.
- 장애가 난 서비스를 리스트에서 쉽게 찾는다.
- AI가 현재 가장 중요한 위험을 요약한다.
- 사용자는 문제 서비스로 바로 들어갈 수 있다.

### 발표 멘트

이 화면은 운영자가 처음 보는 메인 화면입니다.

기존에는 장애가 나면 여러 도구를 열어봐야 했지만, 여기서는 서비스 상태를 한 화면에서 확인합니다.

빨간색으로 표시된 checkout API는 배포 이후 문제가 생긴 서비스입니다.

사용자는 이 화면에서 "지금 어느 서비스가 위험한지"를 먼저 확인하고, 해당 서비스를 선택해서 원인을 따라갑니다.

## 화면 2. 장애 서비스 선택

### 화면 목표

서비스 목록 또는 그래프에서 장애가 난 서비스를 선택하는 장면이다.

### 화면 구성

- 중앙에는 서비스 카드 또는 서비스 연결 그래프를 둔다.
- 각 서비스 카드에는 다음 정보를 표시한다.
  - 서비스 이름
  - 상태
  - Pod 수
  - 최근 배포 시간
  - 최근 에러율
- `checkout-api-v2` 카드만 빨간색으로 강조한다.
- 카드 하단에 "최근 배포 10분 후 장애 감지" 같은 문구를 둔다.

### 이 화면에서 보여줄 기능

- 장애를 단순 목록이 아니라 서비스 흐름 안에서 보여준다.
- 결제 서비스가 주문 서비스, DB, 프론트엔드와 연결되어 있음을 보여준다.
- 사용자는 어디를 눌러야 하는지 고민하지 않아도 된다.

### 발표 멘트

이제 장애 시나리오를 시작하겠습니다.

새 버전 배포 이후 결제 기능에 문제가 생긴 상황입니다.

화면에서는 checkout API가 빨간색으로 표시되어 있고, 최근 배포 이후 상태가 나빠졌다는 힌트가 보입니다.

중요한 점은 장애를 단순히 목록에서 찾는 것이 아니라, 서비스 연결 구조 안에서 어디가 문제인지 빠르게 보는 것입니다.

## 화면 3. 서비스 상세

### 화면 목표

선택한 서비스에서 실제로 어떤 문제가 생겼는지 보여준다.

Komodor의 서비스 상세 화면처럼 Events, Logs, Pods, Metrics, YAML 탭을 참고한다.

### 화면 구성

- 상단 서비스 요약
  - 이름: `checkout-api-v2`
  - 상태: Critical
  - 클러스터: production
  - 네임스페이스: checkout
  - 마지막 배포: 10분 전
- 주요 지표 카드
  - 에러율: 1.1%에서 8.2%로 증가
  - 응답 시간: 180ms에서 2.4초로 증가
  - 사용 가능한 Pod: 3개 중 1개
  - 재시작 횟수: 6회
- Pod 상태
  - `checkout-v2-1`: Running
  - `checkout-v2-2`: 계속 재시작
  - `checkout-v2-3`: 메모리 부족으로 종료
- 로그 패턴
  - `DB timeout`
  - `connection pool exhausted`
  - `readiness probe failed`
- 최근 변경
  - PR #1234
  - image: v1.4.1에서 v1.4.2
  - DB_POOL_SIZE: 20에서 5
  - memory limit: 512Mi에서 256Mi

### 이 화면에서 보여줄 기능

- 장애 상태를 한 화면에 모아 보여준다.
- 사용자가 `kubectl describe`, 로그, 메트릭 대시보드를 각각 열지 않아도 된다.
- 최근 변경과 현재 장애 상태가 같은 화면에 놓인다.

### 발표 멘트

서비스 상세 화면에서는 실제 장애 상태를 확인합니다.

에러율과 응답 시간이 올라갔고, 일부 Pod는 정상적으로 뜨지 못하고 계속 재시작되고 있습니다.

또 최근 변경을 보면 DB 연결 수와 메모리 제한이 줄어든 것을 확인할 수 있습니다.

기존에는 이 정보를 여러 곳에서 찾아야 했지만, 여기서는 하나의 화면에서 문제의 단서를 모아 볼 수 있습니다.

## 화면 4. 변경 위험 분석

### 화면 목표

Git diff를 단순 줄 변경이 아니라 운영 위험으로 해석하는 장면이다.

### 화면 구성

- 왼쪽: Git PR 변경 목록
  - image 변경
  - `DB_POOL_SIZE 20 -> 5`
  - `memory limit 512Mi -> 256Mi`
  - `replicas 3 -> 4`
- 중앙: 변경 위험 분석
  - DB 연결 수 감소: DB timeout 위험
  - 메모리 제한 감소: 메모리 부족 종료 위험
  - Pod 수 증가: 배치 여유 확인 필요
- 오른쪽: 영향 받는 리소스
  - Deployment: checkout-api-v2
  - Pod: checkout-v2-*
  - Service: checkout-service
  - Database: checkout-db
  - HPA 또는 자동 확장 설정

### 이 화면에서 보여줄 기능

- "값이 바뀌었다"에서 끝나지 않는다.
- 그 값이 서비스 운영에 어떤 영향을 주는지 설명한다.
- Git 변경과 Kubernetes 리소스를 연결한다.

### 발표 멘트

이 장면이 저희 서비스의 핵심입니다.

기존 diff는 값이 바뀐 사실을 보여줍니다.

하지만 운영자는 이 값이 위험한지 직접 판단해야 합니다.

저희는 DB 연결 수가 줄어든 것은 DB timeout 위험으로, 메모리 제한이 줄어든 것은 서버가 메모리 부족으로 종료될 위험으로 해석합니다.

즉 바뀐 줄이 아니라, 실제 서비스 영향까지 보려고 합니다.

## 화면 5. AI 원인 분석 채팅

### 화면 목표

사용자가 자연어로 질문하고, AI가 분석 근거를 바탕으로 쉽게 설명하는 장면이다.

Komodor의 Klaudia AI 화면을 참고한다.

### 화면 구성

- 채팅 패널 상단
  - "AI Copilot"
  - "분석 기준: 최근 배포, Pod 상태, 로그, 지표"
- 사용자 질문
  - "어디서 문제가 난 건가요?"
  - "바로 롤백해야 하나요?"
  - "수정하면 어떤 값부터 봐야 하나요?"
- AI 답변
  - "결제 API 배포 이후 DB timeout 로그가 증가했습니다."
  - "동시에 사용 가능한 Pod가 3개 중 1개로 줄었습니다."
  - "최근 변경에서 DB 연결 수가 20에서 5로 줄어든 것이 가장 높은 원인 후보입니다."
  - "메모리 제한도 줄어들어 일부 Pod가 종료된 것으로 보입니다."
- 하단 근거 카드
  - Git 변경
  - Pod 상태
  - 로그 패턴
  - 지표 변화

### 이 화면에서 보여줄 기능

- AI가 원문 로그 전체를 막 읽는 것이 아니다.
- 시스템이 먼저 정리한 분석 자료 안에서만 설명한다.
- 사용자가 이해하기 쉬운 말로 원인 후보와 다음 행동을 제안한다.

### 발표 멘트

이 화면은 AI가 현재 장애 상태를 설명하는 장면입니다.

사용자가 "어디서 문제가 난 건가요?"라고 물으면, AI는 Pod 상태, 로그, 지표, 최근 Git 변경을 함께 보고 답합니다.

예를 들어 "결제 서비스가 위험 상태이고, 일부 서버가 계속 재시작되고 있으며, DB 연결 수가 부족한 것이 주요 원인일 수 있다"라고 설명합니다.

핵심은 AI가 복잡한 Kubernetes 상태를 사용자가 이해할 수 있는 말로 풀어준다는 점입니다.

## 화면 6. Safe PR 제안

### 화면 목표

AI가 직접 클러스터를 수정하지 않고, 검증 가능한 수정 PR을 제안하는 장면이다.

### 화면 구성

- AI 추천 조치
  - DB_POOL_SIZE를 5에서 20으로 복원
  - memory limit을 256Mi에서 512Mi로 복원
  - 현재 배포를 일시 중단
  - 필요하면 이전 버전으로 롤백
- 각 조치별 카드
  - 예상 효과
  - 위험도
  - 검증 결과
  - 필요한 승인자
- 검증 영역
  - dry-run 통과
  - 정책 검사 통과
  - 권한 검사 통과
  - 사용자 승인 대기
- 버튼
  - Safe PR 생성
  - 롤백 PR 생성
  - 더 보기

### 이 화면에서 보여줄 기능

- AI가 바로 운영 환경을 고치지 않는다.
- 수정 후보를 Git PR로 만든다.
- 검증과 승인 조건을 통과해야 반영된다.
- 운영 기록과 책임 소재가 남는다.

### 발표 멘트

이 화면은 복구 방법을 선택하는 단계입니다.

중요한 점은 AI가 바로 클러스터를 수정하지 않는다는 것입니다.

AI는 DB 연결 수 복원, 메모리 제한 복원, 롤백 같은 후보를 제안하고, 시스템은 dry-run, 정책, 권한을 확인합니다.

그 다음 사용자가 승인하면 Git PR로 남기고, GitOps 방식으로 반영합니다.

## 화면 7. 복구 결과와 감사 기록

### 화면 목표

복구가 어떻게 반영되었고, 결과가 좋아졌는지 보여준다.

### 화면 구성

- 복구 결과 카드
  - PR 생성 완료
  - 리뷰 승인 완료
  - 동기화 완료
  - Pod 3/3 정상
- 지표 변화
  - 에러율: 8.2%에서 0.4%
  - 응답 시간: 2.4초에서 190ms
  - 재시작 횟수: 증가 멈춤
- 감사 기록
  - 누가 승인했는지
  - 어떤 PR이 생성되었는지
  - 어떤 설정이 바뀌었는지
  - 언제 반영되었는지

### 이 화면에서 보여줄 기능

- 복구가 감으로 된 것이 아니라 근거와 기록을 남긴다.
- 운영자가 직접 수정한 변경도 Git 기록으로 되돌린다.
- 같은 문제가 반복되면 과거 기록을 참고할 수 있다.

### 발표 멘트

마지막으로 복구 결과 화면입니다.

수정 PR이 반영된 뒤 Pod가 정상화되고, 에러율과 응답 시간이 다시 안정화됩니다.

또 누가 승인했고, 어떤 설정이 바뀌었고, 어떤 결과가 나왔는지 기록으로 남습니다.

그래서 이 시스템은 단순히 장애를 고치는 도구가 아니라, 운영 과정을 추적 가능한 GitOps 흐름으로 되돌리는 도구입니다.

## 데이터 가공 흐름

### 입력 데이터

Git에서 들어오는 데이터는 다음과 같다.

- commit id
- PR 번호
- 작성자
- 변경 파일
- 이미지 버전
- 배포 시간
- 변경된 설정 값

Kubernetes에서 들어오는 데이터는 다음과 같다.

- namespace
- Deployment
- ReplicaSet
- Pod
- Node
- Event
- Condition
- 재시작 횟수
- Ready 상태
- 스케줄링 실패 이유

로그와 지표에서 들어오는 데이터는 다음과 같다.

- 새로 증가한 오류 문장
- 오류 발생 횟수
- 응답 시간
- 에러율
- CPU 사용량
- 메모리 사용량
- DB 연결 사용량
- 배포 전후 변화율

### 가공 단계

1. 배포 ID 연결
   - Git 변경, 이미지, Pod, 로그, 지표를 하나의 기준 ID로 묶는다.
2. 변화 계산
   - 배포 전 30분과 배포 후 10분을 비교한다.
   - 에러율, 응답 시간, 재시작 횟수, 로그 패턴 변화를 계산한다.
3. 분석 자료 생성
   - AI에게 원본 전체를 넘기지 않는다.
   - 필요한 요약만 만든다.
4. 원인 후보 생성
   - AI는 정리된 분석 자료 안에서 원인 후보를 만든다.
5. Safe PR 생성
   - 수정 후보를 Git PR 형태로 만든다.
   - dry-run, 정책, 권한, 승인 조건을 확인한다.

## 저장소 설계

### Redis

Redis는 실시간으로 들어오는 상태 변화를 임시로 모으는 곳이다.

예를 들어 Pod 상태 변경, 로그 발생, 지표 변화, 배포 이벤트 같은 빠른 데이터는 Redis에 먼저 들어간다.

발표에서는 "실시간 캐시"라고 쉽게 말한다.

### PostgreSQL

PostgreSQL은 정리된 결과와 기록을 저장하는 곳이다.

예를 들어 분석 결과, 배포 이력, 승인 기록, PR 기록, 원인 후보, 복구 결과를 저장한다.

발표에서는 "분석 결과 저장소"라고 말한다.

### Object Storage

로그 원문이나 큰 리포트는 DB에 전부 넣지 않고 파일 저장소에 보관할 수 있다.

MVP에서는 필수는 아니지만, 이후 확장 포인트로 둘 수 있다.

## 기술 챌린지 연결

### 1. 변경 위험 분석

기존에는 YAML 줄이 바뀐 것만 보인다.

우리는 변경된 값이 운영에 어떤 위험을 만들 수 있는지 해석한다.

예를 들어 `DB_POOL_SIZE` 감소는 DB timeout 위험으로, memory limit 감소는 메모리 부족 종료 위험으로 바꿔 보여준다.

### 2. 운영 지표 수집과 가공

기존에는 Git, Pod, 로그, 메트릭이 흩어져 있다.

우리는 이 데이터를 배포 ID 기준으로 묶고, AI가 읽을 수 있는 원인 분석 자료로 가공한다.

이 부분에서 Redis와 SQL을 활용한다.

### 3. 안전한 복구 PR

기존에는 운영자가 클러스터를 직접 수정하거나 수동으로 롤백한다.

우리는 수정 후보를 PR로 만들고, 검증과 승인 후 반영한다.

그래서 자동화와 추적성을 동시에 가져간다.

### 4. Pod 배치 분석

Pod가 Pending 상태라면 "왜 배치되지 못했는지"를 분석한다.

CPU나 메모리가 부족한지, 정책이 맞지 않는지, 특정 Node에만 배치 가능한지 확인한다.

이 부분은 PintOS에서 배운 스케줄링과 자원 관리 개념을 Kubernetes 운영 문제로 확장하는 기술 챌린지로 설명할 수 있다.

## 발표용 최종 요약

발표에서 이 문서를 한 문장으로 줄이면 다음과 같다.

> 기존 GitOps는 Git 설정과 클러스터 상태를 맞추는 데 집중하지만, 저희는 배포 전 위험과 배포 후 장애 원인을 Git 변경, Pod 상태, 로그, 지표와 연결해서 분석하고, 검증된 수정 PR로 복구하는 흐름까지 만들고자 합니다.
